# Managed renewal

The external controller uses the existing private session registries and job ledger for agent-only, DevBox and host release windows. It preserves work before replacement, checks the exact session UUIDs through the fixed role runners, and leaves ordinary dispatch paused until every retained session has made fresh progress. A platform repair request carries its affected product job IDs and stays separate from their job and host request records.

## Installation boundary

Install `tools/renewal.py` and its imports in the reviewed, immutable host release at `/usr/libexec/dev-pair/tools`. Install `runtime/renewal/driver` as `/usr/libexec/dev-pair/renewal/driver`. Install the systemd services and timer in the host's unit path, and `dev-pair-renewal.conf` in the tmpfiles configuration. The renewal controller and the fixed driver run as root outside both replaceable environments. The job ledger remains under `dp-checklist` at `/var/lib/dev-pair/checklist-executor/ledger`. A fixed `runuser` helper uses the ledger's existing admission, inventory and backup functions as that account. Import and restore validation occur in the external controller's private area.

Provision the following separately under the corresponding owner and release authority.

## Approval and dispatch

Controller records use UTF-8 JSON. Use private root-owned mode `0600` regular files. The release's exact file bytes identify it as `releases/<sha256>.json` under `/var/lib/dev-pair/renewal`. The schema 1 release has `source_revision`, `config_sha256`, `plan_sha256`, `ledger_contract`, `state_contract` and `components`. The contracts are both `1`. The four component keys are `host`, `devbox`, `maintenance-agent` and `development-agent`. Each names `source_revision`, `config_sha256` and `artifact_sha256`. The agent components also name `codex_version`. The deployment `config_sha256` equals the host component's config digest. The launch plan at `plans/<plan-sha256>.json` has `schema=1`, `maintenance_context_sha256` and `development_manifests` mapping each development job to its exact manifest hash.

An independent admission service writes `requests/agent.json`, `requests/devbox.json` or `requests/host.json` after verifying the approved source, immutable artifacts and compatibility with the retained release. Each schema 1 request contains `operation`, `scope`, `previous_sha256`, `target_sha256`, sorted `affected_jobs` and a short `reason`. Use a stable unique operation ID and retain it across retries. The agent scope allows only maintenance and development agent changes. The DevBox scope allows only its outer component. The host scope allows the host release and its configuration. A combined change needs staged compatible releases.

The trusted job coordinator enrolls each role/job with `renewal.py register <binding.json>` after its ledger checkpoint exists. The role binding uses the session controller's existing immutable fields plus `role`. For a production binding, `provider` is `gptbox`, `policy_sha256` records the admitted Codex configuration digest and `startup_sha256` records the startup manifest digest. The ledger still owns product identity and test checkpoints. Each role's registry owns its selected model and effort. Invoke authorized ordinary turns through `renewal.py turn <turn-spec.json> <prompt.txt>`. The private turn spec contains `operation`, `role`, `job`, `logical_session`, `session_uuid`, and `request_sha256` for the pre-staged schema 2 input. Use `null` for a first turn and the exact prior provider UUID for a resume. The registry leases and authorizes launch before the fixed driver invokes either role. Replaying a registered operation returns the original observation.

## Scheduled and on-demand operation

The engineering schedule is `04:00 Asia/Tokyo`, with persistent missed-run handling. Enable `dev-pair-renewal-agent.timer` and `dev-pair-renewal-recovery.service` after the installation gates pass. The timer and operator use the same service, including candidate resolution. For an on-demand check, start `dev-pair-renewal@agent.service`. The separate deliberate release windows use `dev-pair-renewal@devbox.service` and `dev-pair-renewal@host.service`. These commands consume only approved requests and accept no executable input. The boot recovery service uses the same reconciliation logic and exact interrupted operation.

Before activation, the controller publishes a private `attempts/<operation>/inventory.json` and pins its digest in the journal. It covers every registered job, both role catalogues and provider session bindings, checkpoint hashes, complete uncommitted source and session tree digests, the target release, config and credential references, and host request and attempt identities. It verifies a clean ledger restore, both clean registry restores and the durable tree copies. Active turns drain under their original ownership. Unsafe or unowned operations defer activation until reconciled. The workload's cache stays in its separately managed durable mount.

After replacement, the controller verifies the selected release, restored registry/state identities and the exact outstanding request state. Each role resume must return the same UUID, a complete owned CLI turn, fresh checkpoint-bound progress and the measured image/version through its existing Distrobox placement. The journal records the resulting operation/event/progress digests. Normal role work and host effects can continue only after successful reconciliation. Failed or interrupted replacement invokes the same selector for the verified previous release. Interrupted rollback reads saved proofs and admits only unused verification operations. Ambiguous ownership or state remains held for the independent operator recovery route. The authoritative job ledger and recorded host effect IDs stay in place during rollback.

Inspect the latest journal with `renewal.py status`. Terminal phases are `completed`, `rolled-back` and `deferred`; `blocked` retains the durable fence and recovery evidence. Backups include private source and history. Retain the last compatible release and useful backups within storage policy. The first implementation bounds the entire set at 16 retained sessions, 64 jobs, 32 retained attempt directories, and 512 MiB of source/state copy per attempt. It requires an eight GiB free-space reserve plus copy capacity. A larger set defers as a whole. Clean up only reviewed terminal attempts and retained displaced trees after confirming the live transition and an independent restore; preserve current and prior rollback inputs.

## Evidence

Run `python3 -m unittest discover -s tests -p 'test_renewal.py'` for local component evidence. These tests use real SQLite registries and ledger records, real filesystem trees and an external subprocess, including termination of the controller after a replacement effect and restoration of both missing registry directories. Stock authenticated provider progress, physical Fedora release activation, host reboot, stable tooling CI resolution, scoped broker custody and the actual scheduled firing require the authorized target and its installed services.
