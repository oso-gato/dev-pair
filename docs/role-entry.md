# Headless gptbox role entry

`Gptbox.enter(container_id, sealed_image_id, 'turn')` uses the existing
headless Distrobox route and the image command
`/usr/bin/python3 -I /usr/lib/dev-pair/gptbox/runtime.py entry turn`. The
controller requires the exact running container, its frozen image, the existing
network-none confinement and the declared job mounts. The assembly probe still
uses its three probe mounts and cannot dispatch a turn.

The mounted request in `/run/dev-pair-turn/request.json` supplies one operation
ID, the role, provider, recorded model and effort, the standards pin, the local
endpoint, and the SHA256 of the prompt and both configuration inputs. The role
must match the sealed image. The runtime delivers the validated prompt from
`/run/dev-pair-turn/prompt.txt` on stdin through a sealed in-memory file. Codex
receives the managed startup instruction from
`/etc/codex/requirements.toml` and its validated configuration and frozen
loaders through the read-only binds listed in `TURN_READONLY_MOUNTS`. The fixture
seeds the pinned CLI's bundled skills before mounting them read-only.

`/credentials/api-key` is a separate read-only credential input. This entry
accepts only the fixed synthetic credential and an HTTP endpoint on the isolated
runtime's IPv4 loopback interface. New maintenance input manifests select
`gpt-6.2-sol` at High effort. The launcher passes the request's recorded selection
through, including older selections, and never selects a replacement model.

The runtime creates the operation directory before starting Codex. An existing
directory suppresses another launch for that operation. The CLI writes its
usual rollout under `/state/codex`. Private output and the turn receipt are
written under `/state/turns/<operation>`. A completed turn emits a bounded
summary on stdout.

The entry allows 20 seconds for the CLI and up to two seconds to reconcile
owned descendants. The launcher handles SIGTERM and SIGINT while the turn is
running. Linux reparents detached descendants to the entry process, which
signals children through pidfds after verifying kernel parentage. The entry
confirms cleanup when the kernel reports it has no children left. The failure
receipt records the stop reason and whether owned processes were reaped,
cleanup was unresolved, or launch did not start.
An interrupted operation retains its claim for inspection. A launcher stopped
by SIGKILL can leave a claim without a receipt, which requires observation of
the enclosing runtime before further action.

The focused local fixture runs the exact pinned Codex 0.169.0 executable through
the image entry, checks the model, effort, startup directive, prompt and synthetic
bearer header on the wire, sees a completed assistant turn and verifies the
persisted session rollout. It measures accepted TCP connections, HTTP requests,
WebSocket upgrade attempts and Responses POST bodies before and after duplicate
dispatch. All four deltas must be zero. Run with a locally verified copy of the
binary.

```sh
python3 tests/role_entry_stock.py --binary /path/to/pinned/codex --report /path/to/new-receipt.json
```

The fixture runs locally in isolated Linux namespaces. Live Fedora/Distrobox
turns in both placements, provisioning the admitted job mounts, external model
transport, production credentials and deployment remain open.

## Launch a protected job turn

The host conductor supplies a new digest-bound request for each operation. Both
placements use the same fixed `entry job-turn` and stock Codex start or explicit
UUID resume. The existing `entry turn` described above remains the offline
synthetic fixture.

A trusted conductor stages the files under
`/var/lib/dev-pair/turn-inputs/<role>/<job>/<operation>`. This tree is
root-owned, with traversable protected ancestors and read access for the
appropriate role group. Use read-only regular configuration files and no
symlinks. Bind the staged leaves read-only with the exclusive job SELinux
categories. The host controller supplies the released artifact identities
separately from the workspace.

| Staged input | Contents |
| --- | --- |
| `turn/request.json` | One schema 2 request. Record its exact byte SHA-256 independently before launch. |
| `turn/approval.json` | Byte-identical copy of the separately protected job repository approval for this role's SELinux label. |
| `turn/prompt.txt` | The task or continuation, at most 16 KiB of UTF-8. |
| `turn/startup/` | Manifest plus the seven whole project and shared documents. The controller can load the verified private corpus with `startup_delivery.load_private` from the approved project revision and exact standards cache. Stage the manifest and each `<id>.txt`. |
| `requirements/requirements.toml` | Managed requirements generated by `gptbox_runtime.role_policy(directive, live=True, development=role == 'development')`. The directive orders startup reading and supplies the job-specific operating instructions. |
| `loaders/` | Corresponding `config.toml`, immutable `hooks.json`, `AGENTS.md`, `AGENTS.override.md` and the directories `skills`, `plugins`, `rules`, `agents`, `shell_snapshots`, `.tmp/plugins` and `.tmp/marketplaces`. Seed the released CLI's bundled skills through approved preparation before freezing the mounts. |

The request fields are `schema`, `operation`, `action`, `role`, `job`,
`logical_session`, `session_uuid`, `workspace`, `provider`, `model`,
`effort`, `standards_sha`, `repository`, `candidate_sha`,
`agreement_sha256`, `requirements_sha256`, `config_sha256`, `prompt_sha256`,
`startup_sha256` and `turn_seconds`. Use `schema=2`, `provider=gptbox`,
`workspace=/work/job`, the adopted standards pin and the approved
`owner/repository` and agreement. The candidate SHA must equal the job
workspace's Git HEAD. Stage `action=start` and `session_uuid=null` for a new
logical session. Stage `action=resume` and the original stock UUID for a
continuation. Preserve the recorded role, logical session, agreement, provider,
model, effort and startup corpus. New build work uses the project's selected
GPT-6.2 Sol High profile. The maximum turn allowance is 120 seconds.

The trusted conductor acquires the authorized GitHub repository in a protected
checkout. It records the approved acquisition commit and agreement before
constructing the editable role checkout. A separate protected startup project
checkout can supply the project documents. Pin its revision independently of
the evolving product candidate.

```sh
/usr/bin/python3 tools/gptbox.py approve-job --job "$JOB" --repository "$REPOSITORY" \
  --agreement-sha256 "$AGREEMENT_SHA" --acquired-checkout "$TRUSTED_CHECKOUT" \
  --acquired-sha "$ACQUIRED_SHA" --startup-project "$VERIFIED_STARTUP_PROJECT" \
  --startup-project-sha "$STARTUP_PROJECT_SHA" --standards-cache "$VERIFIED_STANDARDS_CACHE"
```

This approval checks the acquired checkout and loads the exact private
standards through the existing pinned loader. It saves the source commit and
tree, approved repo and startup digest under
`/var/lib/dev-pair/repository-approvals/<job>.json` and the private startup
files in the sibling `<job>/` directory. Copy the exact approval and corpus
into each role's stage. The launchers check the copy against the protected
original. The runtime checks the product worktree origin, actual candidate
HEAD and ancestry from the protected Git commit/tree. It also checks that
the startup files match the approved project revision and exact adopted
standards. Git identity checks run without fetching.

The source tree for a job and its stock session files stay in the role's
`workspaces/<job>`, `state/<job>` and `cache/<job>` under
`/var/lib/dev-pair/<role>`. The runtime publishes a private
`state/<job>/turns/<operation>/result.json` and keeps the stock event log and
stderr at that leaf. Keep the role session and durable operation leases
outside the replaced container. Existing claims require inspection. A fresh
operation may resume the saved stock UUID after the conductor reconciles
pending effects.

### Scoped provider profile

The host-side `tools/provider_broker.py` supports the direct OpenAI API-key
profile. The subscription login flow is a separate profile that this broker
does not implement. Give the broker a protected root-readable credential file,
an approved grant, the exact staged request, its operation socket path and the
protected evidence path. The credential file stays outside all role mounts.
The broker's only upstream routes are the model-availability lookup and
streamed Responses at `api.openai.com` with TLS certificate verification. Model
discovery and an authorized provider response are separate checks.

The grant binds the request SHA to exact local UID and GID, the protected
job allowance by `allowance_ref` and `allowance_sha256`, approved model IDs,
expiry, time and request limits, maximum body bytes, full billable input
ceiling, per-response output-token limit, approved tariffs and the operation
spend ceiling in millionths of a dollar.

The trusted controller records the approved full-input billing contract in
`/var/lib/dev-pair/provider-allowances/<job>/allowance.json`. The closed schema
uses `schema=1`, `kind=verified-full-billable-context`, `auth_profile=openai-api-key`,
`job`, `allowance_ref`, `repository`, `agreement_sha256`, `spend_microusd`,
`expires_unix` and `models`. A model entry contains `max_context_tokens`,
`input_microusd_per_million`, `output_microusd_per_million`, `observed_models`,
`context_evidence_sha256` and `tariff_evidence_sha256`. The evidence files
`<model>.context` and `<model>.tariff` share the protected allowance leaf.
They must establish a conservative billable input ceiling including provider
overhead and local tool schemas, and the worst applicable default-tier text
tariff for every approved observed model. A generic account budget or a guessed
context length provides no launch authority.

The broker reserves the full verified input ceiling plus forced maximum
output before each POST. Every role and future turn for the job uses the same
transactional `usage.sqlite` reservation ledger. An uncertain effect still
consumes its reservation. The transaction binds the normalized request hash
to the operation and attempt before the POST. The broker refuses another
POST for that operation after an uncertain effect, and refuses an identical
normalized body after completion. A completed request can still lead to a
distinct tool continuation. The receipt identifies a blocked repeat and the
original attempt. Reconcile the original effect before issuing a new operation.

Usage, service tier or a reported model outside the verified tariff contract
quarantines the shared job allowance and withholds completion. An unexpected
model is recorded only as a digest. A missing model observation leaves the
operation's effect uncertain. If a crash or storage failure leaves a pending
reservation without a durable outcome, the whole allowance reports
`unresolved` with zero remaining capacity until inspected. In-band provider
failures are forwarded as fixed diagnostics after bounded SSE parsing.

The protected receipt records reservations, observed model and usage and
sanitized failure status. An idle listener closes normally at the approved
expiry. It contains no request bodies, credential strings or startup documents.

The only broker entry below is for a separately authorized live operation.
Precreate the channel directory `/run/dev-pair/provider/<first 32 hex of request SHA>`
owned by root and the target role group with mode 0750 and the role's exclusive
SELinux filesystem label. Keep only its `responses.sock` entry. Provide a
root-owned private evidence directory per role and job. Successful use
requires a listening socket and a recorded exact broker authorization.

```sh
/usr/bin/python3 -I tools/provider_broker.py \
  --grant "$TRUSTED_GRANT_FILE" --request "$STAGED_REQUEST_FILE" \
  --credential-file "$CONTROLLER_CREDENTIAL_FILE" \
  --socket "/run/dev-pair/provider/${REQUEST_SHA32}/responses.sock" \
  --receipt "/var/lib/dev-pair/provider-evidence/${ROLE}/${JOB}/${OPERATION}.json"
```

The job's private network namespace contains only loopback. Codex connects to
the image-owned listener with a local protocol marker. The listener submits the
exact operation digest and one bounded request to the dedicated Unix socket.
The broker checks the actual peer account and SELinux context before forwarding.
The production listener sets its socket context to the matching confined role
context and immediately restores the trusted broker's socket creation context.
Validate the socket inode, both peer contexts and exclusive labels on the
enforcing Fedora target before admitting live use.

### Maintenance and development launch

On the trusted maintenance controller, pass the sealed maintenance image ID and
the protected completed-assembly identities.

```sh
/usr/bin/python3 tools/gptbox.py run-job \
  --job "$JOB" --operation "$OPERATION" --request-sha256 "$REQUEST_SHA" \
  --image "$MAINTENANCE_IMAGE_ID" --context-sha256 "$MAINTENANCE_CONTEXT_SHA" \
  --source-sha "$MAINTENANCE_SOURCE_SHA"
```

On the approved development runner, execute the nested launch as `dp-dev`.
Keep the independently selected manifest and its sealed archive together under
`builds/<job>/inputs/<manifest_sha256>/`. The existing probe continues to use the
flat `inputs/` leaf.

Provision a private `builds/<job>/work` directory on the same bounded block
filesystem with the inner job's label. Its `/build/job` bind allows the
development role to run candidate build outputs. The managed executable search
path still points to immutable image directories.

```sh
/usr/bin/python3 tools/devbox.py run --manifest "$PROTECTED_DEVBOX_MANIFEST" \
  --sha256 "$DEVBOX_MANIFEST_SHA" --operation "$OPERATION" --request-sha256 "$REQUEST_SHA"
```

Both launchers emit the checked image identity and measured stable CLI version
with the role's bounded `turn` receipt. The immutable agent reports a completed
turn only after confirming the terminal stock event, assistant message and
same persisted UUID. Treat any missing or failed receipt as an operation
requiring reconciliation. The host-test conductor uses the separately
authorized job request/result boundary.

The offline transport and budget checks use `tests/test_provider_broker.py`.
Run the stock start and resume fixture with the exact verified Codex binary and
an isolated Linux user/network namespace with bubblewrap.

```sh
PYTHONDONTWRITEBYTECODE=1 /usr/bin/python3 tests/role_job_stock.py "$PINNED_CODEX"
PYTHONDONTWRITEBYTECODE=1 /usr/bin/python3 tests/role_job_stock.py "$PINNED_CODEX" --ambiguous-retry
```

Both tests use synthetic data and no real provider call. The stock fixture
proves command, protocol, durable session and continuation behavior. Enforcing
Fedora placement, provider authorization and the actual model remain separate
acceptance gates.
