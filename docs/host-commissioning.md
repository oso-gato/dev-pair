# Commission the selected Fedora host

Use the verified Hostinger recovery terminal or the named tailnet operator with
separately authorized root access. Follow the [destination inspection and
recovery procedure](destination-release.md) first. Establish the authorized
transport, enforcing Fedora 44, the managed allocation and the protected
maintenance gateway. Keep the independent recovery path available throughout
commissioning. The commissioning command reads these prerequisites through the
existing controllers.

The attended bootstrap calls the commissioning controller after it verifies the
checkout, maintenance gateway and destination. It passes the verified source
identity programmatically. The owner uses the same front-door resume command
when the protected installation settles.

The controller reuses a single eligible full platform already in protected
intake. When intake is empty, an attended resume uses the protected release
trust and GitHub read identity to acquire a full release for the exact reviewed
source. The signed host bundle binds the fixed installation manifest. The
authenticated source checkout binds the fixed checklist recipe.

The controller reuses an approved site profile for the inspected host. On a
fresh installation, it derives the first host and site profiles from the
recorded Day 0 confirmation, the current maintenance gateway and the managed
filesystem. It reserves one 8 GiB placement slot and selects three available
SELinux categories using the existing placement allocator. The slot supplies
capacity and isolation. Repository admission and provider use have their own
protected controls. The commissioning policy and its inputs stay root-owned
and are reused on resume.

The controller reuses a complete protected checklist TLS pair. On an eligible
fresh host it issues dedicated one-year server and conductor certificates with
separate private keys and mutual pins. It publishes the two profiles under
`/etc/dev-pair/checklist-server` and `/etc/dev-pair/checklist-client`. Subsequent
runs join an interrupted publication and verify the same pair. An expired or
incomplete retained pair requires protected recovery before another apply.
The controller measures the account, subordinate IDs and remaining storage
before provisioning the core managed listener. Resume the same Day 0 setup
after independent workload access has been admitted for the selected roles.
Commissioning checks the protected authority for each feature and lists any
remaining prerequisites. Owner intake needs the approved catalogue, startup
material and a valid provider slot. Checklist cleanup needs the managed
validation filesystem. Scheduled publication checks need the independently
approved agent publisher and successful read access to protected main and its
fixed workflow. An empty run list can qualify the schedule. The bridge
verifies signed artifacts before it offers a compatible release to renewal.

This stage uses the approved owner catalogue and slot profiles to activate
owner intake. The protected root terminal can run the first-catalogue wizard
when the approved repository checkout, startup and private standards inputs,
provider authority and reviewed billing evidence are available. A missing or
expired grant requires the authorized provider custodian. A fresh site also
needs controlled repository and startup provisioning and a source for the
normalized billing evidence. [First owner setup](owner-day0.md#resume-and-recovery)

A `pending` result names the specific prerequisite, such as available storage,
protected release trust, GitHub read custody or an eligible attested
publication. A `source-gap` identifies missing intake code or protected inputs
that the controller cannot reconstruct from existing authority. The completed
local maintenance probe remains available while those prerequisites settle.

For diagnostics, the internal controller supports `discover` and `status` on
the verified checkout. `prepare` verifies and retains the policy without
activating workloads. `apply` also prepares the policy when needed and resumes
the managed installation.

The entry verifies the protected package and installs its fixed service
closure. It prepares the root-owned host release store and reads back the
exact signed host bundle before the native installer can touch the role stores.
It stages the exact platform through the native installer, publishes
the local initial release through the renewal resolver and writes both
selectors under its lock. The checklist provisioner initializes independent
history, then observes the signed service under the persistent boot fence.
Recovery verifies the selected instance and clears the fence. A pending phase
names the owned work in progress. Repeat the same command to join it. An
interrupted initial selector write can be completed only from its protected
intent. Reapplication reads a compatible live successor and retains saved work.

The ready response contains the selected local release, the admitted timer
targets and their observed next firing. Automatic workload activation records
its own readback and retains the initial commissioning policy. Each workload
timer checks its current boot, role selection and grant before its service
runs. A later resume disarms a timer whose authority was withdrawn and retains
the job records. Commissioning verifies the effective command, workload guard
and Fedora systemd timeout policy before arming a timer. It publishes the
named operator's constrained sudo rule once owner intake is ready. On the
verified tailnet route, the owner can use the [normal terminal command](owner-intake.md).

```sh
dev-pair start owner/approved-repository
```

Record a native reboot and verify the current release, Q loopback listener and
next timer firing with the same entry. Separate controlled product promotion
and any subsequent rollout require their approved release paths. The local
commissioning fixture exercises ordering and durable readback with isolated
files and a synthetic manager. Fedora and SELinux commissioning remain required
on the selected target.
